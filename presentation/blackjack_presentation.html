Good morning. We built a blackjack engine, a strategy layer, a card counter and a simulation lab. The question was whether a card game could be a serious programming project. We treated the rules as a state machine and the game as a set of experiments. The same engine powers the CLI, the notebook and the tests. Here is a real table. The dealer shows ace-nine for twenty. You have ten-seven for seventeen. The rules are simple: twenty one wins, bust loses, and you can hit, stand, double or split. The house edge comes from turn order. You act first and can bust before the dealer plays. Basic strategy cuts that edge to about four tenths of a percent. Counting does not change the rules. It tracks low and high cards and bets more when the deck is rich, turning the same game into roughly a half percent player edge.

02 · The flow

Every hand follows the same seven steps.

Click a step. The function name is what you would find in engine.py.

Every hand follows seven steps. Validate and deduct the bet. Deal from the shoe. Offer insurance and check naturals. Ask the player for an action. Run the dealer policy only if a hand is live. Settle each hand. Write one HandResult. The UI never decides a rule. It asks the engine for available_actions and calls act. That separation is why the CLI, the notebook and the tests behave the same, and why analytics only has to read the ledger.

03 · Architecture

Three front doors. One engine.

↓
↓

Three front doors, one engine. The CLI, the notebook and the tests all call BlackjackGame. Under it are cards, hands, rules, strategy, counting, analytics, bots, simulation and charts. We chose one shared engine over copying logic into each front door. A fix lands once, and a test at the engine boundary protects every surface. The trade-off is a stricter API, but that is the point.

def act(self, action: str) -> None:
    if self.state is not GameState.PLAYER:
        raise RuntimeError("The table is not accepting actions")
    if action not in self.available_actions():
        raise ValueError(f"Illegal action {action!r}")

    hand = self.player_hand
    if action == "hit":
        hand.add(self._draw())
        if hand.is_bust or hand.total == 21:
            hand.stood = True
        self._advance()

The engine is a state machine: IDLE, INSURANCE, PLAYER, SETTLED. Only PLAYER accepts actions. The first check is state. The second is available_actions. If the action is not legal, it raises. Hit mutates only the current hand. Bust or 21 closes it, then _advance moves to the next split hand. We chose explicit states over loose flags because illegal transitions are the main bug class. The tests assert the transition, not just the final score. That is why the UI cannot ask for a double after a hit.

Every payout is a formula. I will read it left to right. A win returns the stake plus one. A blackjack returns the stake plus one and a half. A push returns the stake. A loss returns nothing. Surrender returns half. Insurance is a separate half-unit bet that pays two to one. The important line is total_wagered. It includes doubles, splits and insurance, because house edge is net divided by all money at risk. Get the denominator wrong and the business number lies.

The strategy layer is three lookup tables: hard, soft and pairs. Pair first. Surrender before the total chart. Then hard or soft. The function returns an action and never mutates the game. We chose tables over a learned model because basic strategy is deterministic, auditable and fast. A model would be harder to explain and harder to test. The chart has 376 cases, and the engine still validates every action the strategy suggests.

def observe(self, card: Card) -> int:
    self.running_count += card.hi_lo_value
    self.cards_seen += 1
    return self.running_count

def true_count(self, decks_remaining: float) -> float:
    return self.running_count / max(0.5, decks_remaining)

The shoe is multi-deck, with a cut card and a discard tray. The Hi-Lo count adds one for low cards, zero for middle cards, minus one for high cards. The running count becomes a true count by dividing by decks remaining. The bet spread uses that true count. The shoe owns the draw and the discard. The counter only observes visible cards. That separation makes the count reproducible in tests, and it is why the simulation can replay the same shoe.

BACKUP · STATISTICS

    
What a physicist will ask.

    

      
What exactly is the house edge?
It is -Σ net / Σ wagered over settled hands. net is after doubles, splits and insurance. wagered is every dollar put at risk, including those extra bets. Win rate is not the edge. The 300k run: 308,277 hands and $3.4M wagered, edge 0.3467%.

      
Why did the 100k edge move to 0.12%?
That is sampling noise. A 100k flat run has a standard error near 0.31 percentage points. The 300k run has SE 0.181 points and a 95% interval of plus or minus 0.355. 0.12% and 0.347% are the same process seen through different sample sizes.

      
Why is Hi-Lo -0.51% but the pool -0.48%?
Edge is dollar-weighted, not an average of percentages. Flat betting wagers more total dollars. Hi-Lo concentrates larger bets at high true counts, so its own line can be player-positive while the combined pool is still house-positive. The pool is dominated by the flat line's volume.

      
How many hands are enough?
SE scales as 1/√N. About 0.31 points at 100k, 0.18 at 300k and 0.10 at 1M. To resolve a 0.1-point difference you need millions. The test suite is code correctness, not statistical power.

      
Is the RNG trustworthy?
Python's random.Random is MT19937 with a uniform shuffle and an explicit seed. The same seed gives the same shoe. It is not cryptographic and not for security. We test composition and reproducibility. For very large studies I would use NumPy PCG64 and run several independent seeds.

      
What does the 300k test assert?
test_house_edge_converges_to_theoretical asserts the flat edge lands between 0.15% and 0.85%. That is a broad guard around the published range, not a 0.01-point proof. It catches a broken engine or a wrong payout. Tighter claims need more hands or a confidence interval.

    

    
Concrete 300k run: 308,277 hands · mean bet $11.05 · edge 0.3467% · per-hand SD $11.10 · SE 0.181 pp · 95% CI ±0.355 pp. This is why the deck says 0.347, not exactly 0.35.

BACKUP · CODE AND DESIGN

    
What a programmer will ask.

    

      
Why a state machine instead of flags?
Four states: IDLE, INSURANCE, PLAYER, SETTLED. act() checks the state, then available_actions(), then mutates. An illegal action raises before it touches a hand. Tests assert the raise. Flags would let a double after a hit or a settlement before the dealer plays slip through.

      
How do you prove split hands do not bleed?
Each Hand owns its bet, cards, stood and surrendered flags, and split origin. _settle() writes one HandResult per hand. Tests cover independent wagers, one win and one loss, split aces, resplit and DAS. total_wagered includes both bets and any double.

      
Why floats for money?
Every public money mutation is rounded to two decimals, and tests compare cents. It is not integer-cent accounting. For a teaching simulator that is enough. For production I would use integer cents or Decimal. That is the first thing I would change under audit.

      
What was the hardest bug?
A stale settlement guard let a later round skip settlement. start_hand() now resets round state before dealing, and test_blackjack_on_later_rounds_still_pays locks it. The ledger invariant test runs 300 random hands and checks bankroll equals starting plus the sum of nets.

      
Why Python, and what breaks at scale?
Python gives readable rules, Rich, Plotly and a notebook. The hot loop is object-heavy. 100k to 300k runs are fine, billions are not. At that scale I would vectorize the shoe and settlement, or move the inner loop to Cython, Rust or NumPy.

      
How did AI change the work?
AI helped draft prose and review code. It did not own the design. We can trace why each state exists, why the ledger is shaped this way and why strategy is a table. If asked, open the code and the tests, not the chat.
